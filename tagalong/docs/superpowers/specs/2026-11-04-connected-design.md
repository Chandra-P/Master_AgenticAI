# Tagalong connected application

Approved direction: the architecture agreed in chat, followed by the user's instruction to build a real tested public app. Preserve the browser demo while implementing authenticated connected mode. Stack: Next.js, FastAPI, LangGraph, OpenAI Responses/embeddings, Pinecone, Supabase Auth/Postgres/Realtime. Deploy frontend and backend as separate services on Render unless an existing host is selected. No live service is claimed without verification.

## Architecture and contracts
Normal CRUD bypasses LangGraph. FastAPI verifies Supabase bearer sessions and plan membership on every plan route. Postgres holds versioned JSON plan documents plus normalized membership, proposals, sources, and ingestion jobs. RLS denies direct mutations; transactional server RPCs use optimistic concurrency. Realtime is an invalidation signal; refresh through the authorized API. UI never silently falls back to demo if connected mode fails.

Frontend contract: GET /health -> {status,mode,capabilities}; GET /v1/me -> {id,email,name}; GET /v1/plans -> Plan[]; POST /v1/plans body {kind,title,start,end,participants} -> Plan; GET /v1/plans/{id} -> Plan; PUT /v1/plans/{id} body {plan:Plan,expected_revision:number} -> Plan; POST /v1/plans/{id}/assistant body {message:string} -> {text,preferences:[{label,confirmed:false}],sources:[{id,title,text}],mode:'live',proposal_ids:string[]}; GET /v1/plans/{id}/proposals -> Proposal[]; POST /v1/plans/{id}/proposals/{proposal_id}/confirm body {} -> Plan; POST /v1/plans/{id}/members body {email:string} -> {status:string}. Membership addition only by owner and only for existing signed-in accounts; no unsolicited email. Owner may share plan with known email. Profiles resolved server-side.

Plan uses existing src/services/types.ts fields plus revision:number, owner_id:string, role:'owner'|'member'. Member has optional user_id:string. Message has optional user_id:string and sources. Connected actor's vote key and author are actor.name, unique name derived from email/account ID to avoid impersonation; backend validates actor identity. Existing UI snapshot updates must not overwrite membership, AI proposals, owner/revision or other people's votes/messages. Reject conflicts with 409; client reloads and reports unsaved action. Server controls AI proposal/confirmation and confirmed preferences. Assistant persists its response and pending proposals, then client refreshes plan.

## AI and evidence
LangGraph routes exact plan facts directly to Postgres context, retrieves historical evidence conditionally, and calls Places when configured and relevant. OpenAI returns structured output. RAG namespaces are tagalong:{plan_id}, sources are revalidated against current plan ownership/version before generation and citation. Retrieved text is untrusted evidence. Model cannot mutate plans or execute actions. Durable leased jobs ingest changed/deleted message/document sources with bounded retry and stable vector IDs. Text documents first; unsupported upload types rejected. Uploaded documents private. Budget is authoritative server data. Calendar writes remain disabled until a real OAuth connection and approved executor are configured; do not expose nonfunctional success controls.

## Quality and release
Meaningful backend tests cover auth rejection, cross-plan access, concurrency conflicts, impersonation, vote replacement, proposals, RAG isolation/stale source handling, jobs and provider failure. Browser tests exercise demo and connected mode, loading/errors, auth, plan creation, assistant citations, proposal confirmation and member sharing. Run lint, typecheck, production build, Playwright desktop/mobile, backend tests. Live service tests and public URL smoke required before public-release claim. No secrets in tracked files or logs. CI runs credential-free suites; deployment configuration documents secrets and migration steps.

## Decisions
Retain single modular FastAPI service with a worker process. Demo remains explicitly synthetic; connected mode requires real credentials and never invents users, venues or AI results. A separate production key is preferable but authorized existing project OpenAI/Pinecone keys may be reused locally without disclosure. User accounts/hosting still require connected credentials. Existing original standalone repos remain intact. No unrelated workspace files changed.
