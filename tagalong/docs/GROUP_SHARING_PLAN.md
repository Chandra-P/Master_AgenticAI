# GroupShare — approved scope and implementation

Owner approved November 9, 2026. Branch: `GroupShare`, based on main `ec28228`. Scope: connected, signed-in workspace only. Demo sharing, collaborative editing, outbound invitations and automatic plan membership are excluded.

## Expected behavior

- Existing and newly created groups remain private until the owner selects **Share with members** in a read-only details dialog.
- Added adults with matching verified account emails see the shared group, its theme, owner alias and adult aliases. Contact emails and legal names stay owner-private.
- Names/contact IDs never establish account identity. Missing emails do not grant access. Matching is checked from the authenticated actor each request, not a client-supplied account ID or editable user metadata.
- Members have view-only access. Owner editing, archive/restore, removal and creating plans from a roster remain owner-only. Shared group access never grants plan access.
- Clicking the connected card opens details; edit/plan/archive/remove controls remain independent. Keyboard Enter/Space opens details and closing restores focus.
- Owner can stop sharing. Roster changes update email-based access. Details fetch current authorized data and refresh on focus/visible polling; stale sharing changes are rejected through revisions.

## Files and storage

Backend `groups.py` implements read projection, verified-email visibility and owner-only sharing endpoint. `core.py` adds a default-false verified-email field from trusted provider confirmation. Existing private state JSON gains a backward-compatible `shared` flag; API-only role and owner label are derived. No SQL migration or dependency changes.

Frontend group contracts/service/store support details and sharing with account-generation guards. `groups.tsx` mounts `group-details.tsx` only in connected mode. Styles reuse product tokens. Group picker exposes owned rosters only; existing demo storage and interaction stay unchanged. The editor describes the impact of editing a shared roster.

## Verification and risks

Backend tests cover explicit sharing, legacy privacy, verified identity, outsider/member mutation denial, contact redaction, alias spoofing, revisions, revocation, archive/delete, and separation from plan access. Connected browser tests cover independent owner/member sessions, card and keyboard opening, focus restoration, owner controls, private contact exclusion, stale approval and revocation. Existing frontend/demo and shared suites provide regression coverage.

Primary risks: incorrect identity matching, disclosure of contact fields, unintended plan privileges, and stale account responses. Mitigations are trusted provider confirmation, server-side redaction/authorization, unchanged owner-only plan roster access, and generation guards/fresh reads. Visible pages poll rather than offering realtime group subscriptions. Test fixtures simulate identity/providers; passing them does not verify live Supabase or deployment.

Frontend and API updates must be released together for this feature. Existing private groups require the owner's explicit sharing action after release; no data backfill enables sharing. A fresh clone uses the normal documented dependencies and test fixtures; no required artifact lives in `workspace/`.
